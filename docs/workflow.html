Quy trình làm việc nhóm với LAN Agents

Đi từ tài liệu BA tới code đã merge: nhiều agent trên nhiều máy làm việc, còn người chỉ duyệt ở ba điểm.

Đây là quy trình đích. Quy trình cần 5 tính năng chưa có trong mã hiện tại. Xem Tính năng cần có để biết phần nào đã có nền. Bản chữ đầy đủ nằm ở docs/workflow.md.
Người quyết định

Duyệt phạm vi, hợp đồng API và PR. Trả lời câu hỏi khi agent thiếu thông tin. Chỉ người được merge.

Agent thực thi

Đọc tài liệu, tách task, viết code, chạy test, review chéo, viết báo cáo. Agent của ai chạy trên máy người đó.

Nhóm ví dụ: bốn người, bốn máy

Tech lead · Máy 1
Claude · vai PM và SA
  • Duyệt phạm vi
  • Duyệt kiến trúc
  • Duyệt hợp đồng API
Dev BE · Máy 2
Claude · vai BE
  • Duyệt hợp đồng API
  • Duyệt PR backend
Dev FE · Máy 3
Cursor · vai FE
  • Duyệt hợp đồng API
  • Duyệt PR frontend
QA · Máy 4
Gemini · vai Tester và review chéo
  • Duyệt kết quả kiểm thử

Trước khi bắt đầu: repo có CLAUDE.md chung, mỗi máy trỏ thư mục làm việc vào repo và bật giới hạn trong thư mục làm việc, mỗi máy chỉ cấp quyền cần cho vai của mình, và có kênh Slack đã nối bot.

Bảy bước, ví dụ tính năng “Quản lý đơn hàng”

Người Agent Điểm duyệt Bấm vào từng bước để xem chi tiết.
1
Khởi tạo Tech lead Tạo chủ đề từ Slack, gắn tài liệu BA, chọn mẫu quy trình. 
/lan new "Quản lý đơn hàng" --template feature --doc BA-don-hang.docx --team BE,FE,Tester

Bot tạo chủ đề theo mẫu Tính năng mới, mời các máy vào nhóm và gắn tài liệu BA.

2
Đọc tài liệu và hỏi lại Agent PM BA / PO trả lời Agent liệt kê chỗ mơ hồ trong tài liệu BA. Người trả lời trên Slack.

Ví dụ câu hỏi: Đơn bị hủy sau khi đã thanh toán thì hoàn tiền tự động hay thủ công?

Câu trả lời được ghi vào chủ đề để mọi agent cùng đọc.

Không bỏ bước này. Tài liệu BA mơ hồ là nguyên nhân phổ biến nhất khiến agent làm sai.
3
Tách task Agent PM Điểm duyệt 1 · Tech lead Agent tạo bảng task có phụ thuộc. Chưa duyệt thì không ai được code.

Tech lead kiểm tra phạm vi đã đúng chưa và task nào quá lớn, sửa rồi bấm Duyệt. Sơ đồ task nằm ở mục Bảng task bên dưới.

4
Hợp đồng API Agent SA Điểm duyệt 2 · Dev BE + Dev FE Agent viết openapi.yaml và schema. Duyệt xong thì hợp đồng bị khóa.

Muốn đổi hợp đồng sau khi khóa thì phải tạo yêu cầu thay đổi, và cả hai bên duyệt lại.

Đây là điểm duyệt quan trọng nhất: hợp đồng sai thì cả BE và FE cùng làm lại.
5
Làm song song Agent BE Agent FE Mỗi agent một nhánh, trên máy của mình. Người không cần ngồi xem.
  • Agent BE trên máy 2, nhánh feat/don-hang-be: task #2 rồi #3, mỗi task một commit, chạy unit test trên máy thật.
  • Agent FE trên máy 3, nhánh feat/don-hang-fe: dựng mock từ hợp đồng, làm #4 và #5 cùng lúc với BE.
  • Nếu BE cần đổi API: agent BE gửi yêu cầu đổi hợp đồng, agent FE được báo, người duyệt như bước 4.

Slack chỉ báo khi task xong, khi agent bị chặn, hoặc khi cần người duyệt. Xem sơ đồ làm song song.

6
PR và review Agent review khác hãng Điểm duyệt 3 · Dev BE / Dev FE Agent mở PR, model khác hãng review, CI chạy test, người duyệt và merge.
  1. Một agent khác hãng review, ví dụ Gemini review code Claude viết. Agent tác giả sửa theo comment.
  2. CI chạy test. Test hỏng thì agent tự sửa, không chuyển cho người.
  3. Người duyệt PR cuối cùng, comment trên diff, agent sửa theo.
  4. Chỉ người được merge.
7
Kiểm thử và chốt Agent Tester Agent PM Test theo từng tiêu chí chấp nhận, rồi viết báo cáo KẾT QUẢ.

Agent Tester viết test theo đúng từng tiêu chí chấp nhận trong tài liệu BA và chạy kiểm thử tích hợp trên máy 4. Khi mọi test đạt, agent PM viết báo cáo gồm:

  • việc đã làm và các PR liên quan;
  • tiêu chí chấp nhận nào đã đạt;
  • quyết định đã chốt, lưu vào bộ nhớ dự án;
  • việc còn tồn.

Báo cáo được gửi vào Slack và cập nhật ticket Jira.

Thời gian của người

Ước lượng cho một tính năng cỡ vừa. Chưa có số liệu đo thực tế. Thời gian của người dành cho quyết định và review, không phải để gõ code.

BướcNgười làmThời gian
1. Khởi tạoTech lead5 phút
2. Trả lời câu hỏiBA hoặc PO15–30 phút
3. Duyệt task Duyệt 1Tech lead10–15 phút
4. Duyệt hợp đồng Duyệt 2Dev BE và dev FE20–30 phút
6. Duyệt PR Duyệt 3Dev BE, dev FE15–30 phút mỗi PR
7. Đọc báo cáoCả nhóm10 phút

Nên và không nên

Nên

  • Tài liệu BA có tiêu chí chấp nhận đánh số, ví dụ AC-1: Đơn chưa thanh toán được hủy không mất phí.
  • Làm hợp đồng trước, code sau.
  • Chia task nhỏ: khoảng một PR, dưới 400 dòng thay đổi.
  • Để model khác hãng review nhau.
  • Đặt giới hạn lượt cho mỗi task để agent bế tắc thì dừng và hỏi.
  • Lưu quyết định vào bộ nhớ dự án sau mỗi chủ đề.

Không nên

  • Đưa tài liệu BA sơ sài rồi để agent tự đoán.
  • Cho agent tự merge, hoặc bỏ điểm duyệt để chạy cho nhanh.
  • Để một chủ đề ôm cả một module lớn.
  • Ngồi xem từng lượt agent nói.
  • Cho hai agent sửa cùng một nhánh hoặc cùng một file.

Đo hiệu quả

Sau ba đến năm tính năng, so với cách làm cũ. Nếu các số này không tốt hơn thì chưa nên mở rộng cho nhiều nhóm.

1
Thời gian từ tài liệu BA tới merge.
2
Số giờ người bỏ ra cho mỗi tính năng.
3
Số bug QA hoặc production phát hiện sau merge.
4
Số lần agent bị chặn hoặc phải hỏi lại. Cao nghĩa là tài liệu BA hoặc hợp đồng chưa đủ rõ.
5
Chi phí token cho mỗi tính năng.
